# Case study: a citation-verified research paper workflow, and what live runs taught about context

This is a write-up of building Research Desk, a LangGraph workflow that turns an assignment into a
cited, literature-based paper. It covers the design, the problems that only appeared against real
services, and one open question about long-context behavior that the project raises but does not answer.

Everything in "What was measured" comes from runs and tests in this repo. Everything in "What was not
measured" is a hypothesis or a plan, and is labeled as such.

## 1. The problem

Drafting a research paper with an LLM has two failure modes that matter more than fluency:

- **Fabricated or misattributed citations.** A model will happily cite papers that do not exist.
- **Drift from the brief.** Word limits, required sections and citation style get ignored quietly.

The goal was a system where those two failures are caught by code, not hoped away by prompting, and
where a human approves the direction (topic and thesis) before any drafting effort is spent.

## 2. Architecture

```
assignment -> analyst -> topic (human approves) -> scout: OpenAlex / Semantic Scholar, then Crossref check
           -> thesis (human approves) -> planner -> writer -> critic, loop up to 4 rounds -> paper
```

Around the graph: a FastAPI service, a Postgres table that acts as both run store and job queue
(`FOR UPDATE SKIP LOCKED`), LangGraph checkpoints in Postgres, and a worker that resumes a run from its
last checkpoint after a crash or deploy. A small web UI shows live progress and the approval gates.

### Decisions and the alternatives not taken

| Decision | Why | Alternative not taken |
|---|---|---|
| Fixed graph with deterministic routing | Cheaper, testable, fits free-tier rate limits | An LLM supervisor choosing the next agent |
| Citations verified in code (DOI must resolve in Crossref, title and year must match) | The one guarantee that must not depend on model behavior | Asking the model to only cite real papers |
| Reference list generated by code from cited, verified sources | The model cannot invent a reference entry | Letting the writer produce the bibliography |
| Human approval at topic and thesis | Cheapest points to correct direction | Approval only at the end |
| Run store and queue in Postgres | One datastore, durable, resumable | Redis or SQS plus a separate state store |

**What this is, precisely.** It is a workflow with specialist LLM roles, not autonomous agents. No model
chooses its own tools, and no LLM decides the order of steps. The only dynamic decisions are the two human
approvals and the critic's choice between "rewrite" and "find more sources". Source search and citation
checking are plain code.

## 3. Context engineering, and where "Lost in the Middle" fits

Liu et al., "Lost in the Middle: How Language Models Use Long Contexts", reported that models use
information near the start or end of a long context better than information buried in the middle. That
raises a practical question for any pipeline that stuffs retrieved material into a prompt: how much
context helps, and how much becomes noise?

This project made several context decisions. Their honest status:

| Decision | Actual motivation | Consistent with the paper's idea? |
|---|---|---|
| Keep only the 15 most relevant sources | Prompt hit a provider token cap (see section 4) | Yes, less noise |
| Rank sources by relevance before verifying and prompting | Search returned off-topic papers | Yes, best material first |
| Truncate abstracts to 400 characters | Token cap | Yes, smaller context |
| Each paper section sees only its assigned sources | Keeps writing focused | Yes |
| Critic sees only the body and the sources it cites | Token cap, and the reference list is code-generated | Yes |

These decisions were driven by hard limits and observed failures, not by the paper. They happen to agree
with its direction. The project did not test the paper's claim.

Note on scope: the prompts here are short, a few thousand tokens. The paper's effect was reported for much
longer contexts, and newer models may show a smaller effect. Nothing in this project is evidence for or
against it.

## 4. What was measured

Live runs against Groq (`openai/gpt-oss-120b`, on-demand tier) and real OpenAlex and Crossref, plus an
automated suite of 67 tests including integration tests against a real Postgres.

| What happened | Evidence | Fix |
|---|---|---|
| A single prompt exceeded the provider's per-minute token cap | Thesis request of 8,779 tokens against a limit of 8,000; a later critic request of 8,086 | Cap sources at 15, truncate abstracts, critic sees body and cited sources only, warn on large prompts |
| Off-topic sources in the pool | 42 verified sources included an edge-computing paper for a last-mile delivery query | Rank by relevance, verify in rank order, stop when full |
| Length limit missed | First draft 2,086 words against a 1,500 maximum; the count wrongly included a 369-word reference list | Count the body only, on the rendered text the reader sees |
| Length would not converge | Draft lengths across revisions of one run: 1,610, 1,565, 1,416, 1,576. Sections overshot targets by up to about 35% | Rescale section budgets from measured length; return the best draft that met every mechanical check when the revision cap is reached |
| A section came back with 1 word | Draft 3 of one run had an Analysis section of 1 word | Retry degenerate output; treat any section under 40 words as a hard issue |
| Reviewer judged text the reader never sees | Critic complained about `[S1]` markers and word count on the internal draft | Critic now reviews the rendered paper and is told length is code-checked |
| Duplicate citation styles | Prose contained both `(Author, Year)` and `[S4]` | Writer cites only with markers; code renders APA in-text citations and the reference list |
| Invented statistics | Critic flagged "12% fuel reduction" as unsupported by any source | Writer instructed not to state numbers absent from abstracts; critic flags them |
| Pointless retries | Auth (401) and oversized (413) errors were retried three times | Non-retryable status codes skip straight to the fallback provider |
| Schema setup failed only on real Postgres | Multi-statement SQL rejected with prepared statements; in-memory tests could not catch it | Execute one statement at a time |

Cost and speed observed: about 35,000 to 39,000 tokens and roughly 3 to 4 minutes per paper. Groq's free
tier allowed 200,000 tokens per day for this model, about five papers, and the limit was reached during
testing.

## 5. What was not measured

- **Paper quality.** There is no golden set and no human rating of argument quality.
- **Claim-level accuracy.** Every reference is matched to a Crossref record, but whether a sentence is
  faithful to its source is judged only by an LLM reviewer. That is not proof.
- **Any effect of context order or size on output.** See section 6.
- **The best-draft-on-cap behavior in a live run.** It is covered by tests with a scripted model only.
- **Success rate.** Of the live runs that reached the end, none finished approved by the reviewer. All were
  flagged for human review, mostly for word-count misses. The later fixes (length rescaling, best-draft
  fallback) were not confirmed by a further finished live run, because the daily token quota ran out.
  About six live runs is far too few to report a rate.

## 6. Proposed experiment: does source position matter here?

A small, honest test of the Liu et al. idea on this pipeline. Not yet run, because it needs model quota.

- **Variable:** position of the most relevant sources in the writer and critic prompts: first, middle,
  last. Everything else fixed, including sources and assignment.
- **Sample:** 6 to 8 real assignments, each run in all three conditions.
- **Metrics:** citation validity (code-checked), required-section coverage, how often the reviewer
  approves without flagging unsupported claims, tokens per run.
- **Expectation, stated in advance:** little or no difference at these prompt lengths. A null result is a
  legitimate finding and should be reported as one.
- **Threats to validity:** small sample, one model, a reviewer that is itself an LLM, run-to-run
  variance. Repeat each condition at least twice before drawing a conclusion.

## 7. Limits of the system

- Suited to literature-based papers on topics with DOI-indexed papers. Not for original research, books,
  non-English sources, or work that needs full-text reading.
- Sources are read at abstract level.
- Only APA formatting is implemented, and word limits are approximate.
- Output is a researched first draft to verify and rewrite, not a finished submission.
